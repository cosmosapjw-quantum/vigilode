# 런타임과 구버전 연결

## 기본 실행

내장 규약 1.0.0을 기본으로 실행하라. 현재 실행 모델의 신뢰 가능한 metadata는 provenance로 기록하고, 실제 도구·파일·연결·실행 권한으로 작업 경로를 정하라. 미확인 모델 이름 때문에 내장 연구 흐름을 차단하지 말라.

요청에 필요한 실제 기능만 사용하라. 문헌·최신 사실은 원전과 공식 출처를 확인하고, 대수·미분·계산에는 실제 사용할 수 있는 기호·수치 도구를 선택하라. 도구가 없으면 현재 조건에서 수행할 수 있는 유도·대안·준비 작업을 완료하고 특정 의무를 정확히 인계하라. 사용자의 필수 도구 선택은 그대로 관리하라.

병렬 작업에는 서로 독립적인 과제, 공통 가정·자료 identity, 출력 계약과 합류 지점을 지정하라. 각 agent의 모델 이름에 따라 과학적 계약을 바꾸지 말라. 독립 검토에는 원자료를 제공하고 실제 독립성·검토 방법을 기록하라. 강한 no-go의 독립 검토 범위는 공통 정책 NG7을 적용하라.

프로젝트의 이론 전용·경량 계산·외부 heavy 실행 선택을 존중하라. 구체적인 오류가 있는 프로젝트 규칙은 공통 정책에 따라 교정하라. 현재 계산 권한, 실제 비용과 사용자 고정 목표를 확인하고 실행을 배치하라.

## 명시적 구버전 경로

사용자가 아래 원본 버전을 명시하면 `MODEL_ROUTER.json`의 고정된 identity와 원본 entrypoint를 사용하라.

| 사용자 선택 | resolver 인수 | 원본 |
|---|---|---|
| GPT-5.6 하네스, gpt56, v3.1.0 | `--harness gpt56` | 연구·코딩 v3.1.0 |
| 기존 Astra 하네스 v4.0.0 | `--harness gpt6-astra` | 연구·코딩 v4.0.0-20260908 |
| 현재 모델별 구버전 자동 선택을 명시 | `--model '<확인된 라벨>'` | registry의 정확한 alias에 해당하는 원본 |

단순히 Astra 또는 최신 모델을 사용한다는 언급은 내장 규약의 모델 provenance로 다루라. “기존 Astra 하네스”처럼 원본 선택을 명시한 경우 위 경로를 사용하라. 서로 다른 원본 선택의 차이가 실제 작업에 중요하고 확인할 근거가 없으면 해당 선택만 짧게 확인하라.

resolver는 패키지 선택만 수행한다. 모델 확인·전환, 파일 읽기·실행의 근거는 실제 작업에서 기록하라. CLI는 `--harness gpt56|gpt6-astra`, `--task research|coding|both`를 지원한다. 알 수 없는 model label은 MODEL_UNRESOLVED, registry 오류는 CONFIG_ERROR로 반환한다.

registry의 stable library_file_id로 현재 Library 절차를 사용해 원본을 취득하라. 이미 읽을 수 있는 동일 바이트가 있으면 재사용하라. registry의 SHA-256과 실제 바이트를 확인하고 START_HERE, 해당 핵심 지침, 현재 프로젝트 state와 필요한 phase를 읽어라. ID가 해소되지 않을 때만 해당 고유 파일명으로 검색하라.

Library 접근이 없으면 제공된 첨부나 프로젝트의 정확한 버전을 사용하라. 명시적으로 필요한 원본을 확보할 수 없으면 해당 패키지와 취득 경로를 특정하라. 원본에 독립적인 승인 작업은 계속하라.

## 원본과 현재 정책의 적용

원본 ZIP의 identity와 문서는 보존하라. 현재 사용자의 문체·watchdog·no-go·override 지시를 원본 사용에도 적용하라. 원본 동작의 역사적 재현을 명시한 경우 재현 대상 규칙과 현재 작업의 결정을 구분해 기록하라.

구버전의 일반 STOP, 고정 탐색·재시도 횟수, 잠정 형식화 금지, 반복 승인, 별도 reviewer만 허용하는 규칙은 현재 승인된 정책과 실제 독립 검증 방법에 맞게 해석·교정하라. 명시된 정확도·예산·연구 대상과 과거 실패의 의미는 보존하라.

Astra 원본의 보존된 `.agents/skills/`와 과거 validation 기록은 해당 원본의 역사적 참조로 읽어라. 새 기본 경로의 활성 지침은 이 스킬의 공통 정책과 R/C 참조다. 오래된 “survivor only”·반복 상태 파일 생성·불필요한 부정 단서 필드는 공통 정책에 맞추어 교정하라.

기존 포장 validator의 결과는 패키지 구조 근거로만 재사용하라. 내장 상태와 과학적 결과는 현재 계약과 실제 내용으로 확인하라. 작업 재개에 legacy initializer의 force/reset을 사용하지 말라. 새 JSON initializer는 이미 있는 파일을 덮어쓰지 않는다.

구버전 단계의 의미 대응과 상태명은 `EVIDENCE_AND_HANDOFF.md`를 사용하라. 과거 진행 번호는 실제 유도·검증·출처와 대조해 연결하라.
