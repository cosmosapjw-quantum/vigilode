PLAN OF THE ARMS (frozen definitions in PREDECLARED.json "arms"; this is how they are realised)
- S8: CheckColumns::Sample(8) (today's default; unchanged).
- FA: CheckColumns::All (today's option; unchanged code path).
- FA_P (new option): the n single-column evaluations of CheckColumns::All on the client's pool; P = 2, 4, 6
  workers (threaded clients carry the RhsPurity acknowledgement). The base re-evaluation on the calling thread
  stays as today. Every comparison is the comparison of FA. Columns are handed out in increasing order from
  an atomic counter to P workers with one (state, f1) scratch each; the reported failure is that of the
  smallest failing column (and inside it the first row in FA's order), which is the failure FA meets first,
  so the decision is FA's by construction (tested, discriminator E). Workers skip columns above the smallest
  failure found so far (changes only the number of evaluations of a failing check, not the decision).
- MC (new option, coloured route only): the multi-colouring check of PREDECLARED.json mc_construction:
  construction B (moduli m_r >= lower + upper + 1, pairwise coprime, increasing, until the product >= n) and
  construction G (c1 refined by q(j) mod p_r, primes until the product >= the largest c1 class); the one with
  the smaller total of non-empty groups (equal: B); the tuple map (c1 included) checked injective before the
  check runs (failure = a configuration defect, not a verdict); for every further colouring and every group:
  shift the group, one RHS, restore, every declared entry of the group compared bit for bit with the
  client's assembled entry (from c1), and the uncovered-row test; typed errors name the row, the column (for
  entries) or the group (for uncovered rows), and the colourings. Groups are generated on the fly (j mod m,
  or a stride through a c1 class), not stored. Columns checked = n.
- MC_P (new option): MC with the groups of every colouring handed out to the pool's workers (6); the
  reported failure is that of the first (colouring, group) in MC's sequential order, so the decision is MC's.
- On a sequential client the pooled options run on the calling thread (no pool and no purity
  acknowledgement exist there).
- MC every build (exploratory): a wrapper in the measurement target requests MC before every linearization.
- FA_B (exploratory): a batched right-hand side of nlkpp-dense-n400 written in the measurement target:
  k shifted states per call, each state's convolution summed in the order of the single evaluation
  (vectorised across states), bits checked against the single evaluation; cost per evaluation reported.
