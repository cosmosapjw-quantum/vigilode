# V19·V21: banded stage solve kernel 결과 (loop L1)

이 문서는 `build_report.py`가 `RESULTS.json`과 `RESULTS_V21.json`에서 생성한다. 숫자는 모두 두 파일에서 읽는다.

**정정 고지 (2026-11-23, 독립 리뷰 `REVIEW.json`)**. 이전 판의 2절은 틀렸다. (1) V19의 해석: '의존 사슬 가설이 반증됐고 kernel은 명령어 수에 묶여 있다'고 썼으나, 판정 측정에서 대입 순서만 바꾼 arm B는 같은 명령어 수로 cycle이 절반 가까이 줄었다. KILL 판정은 유효성 규칙에서 나온 것이고 가설의 반증이 아니다. (2) 2절의 표가 판정에 쓴 측정이 아니라 바쁜 host의 첫 측정이었고, 분할 arm이 더 느리다는 문장은 판정 측정과 맞지 않았다. (3) BD는 선언 밖 사후 arm이다. (4) 결과 파일에 없는 숫자를 본문에 적었던 곳을 지웠다. (5) stage b의 측정은 '전체 실행'이 아니라 시도 2-40의 시도당 명령어다. 동결 판정(KILL, PASS-I, PASS-C, PASS)은 모두 그대로이며 리뷰가 원자료에서 다시 계산해 일치를 확인했다.

용어: **stage pattern** = RODAS5P 시도 1회의 선형대수(분해 1회 + solve 8회). **A0** = 보호 client `BandedStageLu`(Indexed kernel, facade의 banded 경로가 쓰는 kernel). **cycles** = 고정 core에서 잰 user-mode CPU cycle. **instructions** = user-mode 명령어 수(결정적, 호스트 부하와 무관).

해석 (독립 리뷰 뒤 정정). KILL은 유효성 규칙에서 나온다: 선언된 arm 중 V2·V3를 통과한 것은 C8과 CV8뿐이고, 둘 중 빠른 C8이 A1의 0.863(n = 1e4)과 0.887(n = 1e5)로 kill 수준 0.77 위다. 가설(대입이 의존 사슬에 묶여 있다)이 반증된 것은 아니다. 대입 순서만 바꾼 arm B는 stage pattern당 명령어가 A1의 1.060배와 1.060배인데 cycle은 A1의 0.565과 0.575이다. 즉 의존 사슬은 실제 비용이다. B는 backward error가 기준 1e-14를 넘어(위 표) 유효 arm이 아니었고, 그래서 판정에 들어가지 못했다. 분할 arm C2·C4·C8은 판정 측정에서 A1의 0.846-0.887로 A1보다 빠르지만 kill 수준에는 못 미친다. 검증을 붙인 CV arm은 A1의 1.174-1.248로 더 느리다. 명령어 수(V21의 tight loop)와 의존 사슬(대입 순서)은 solve 비용에서 따로 작용하는 두 요인이다.

## 3. 의미와 남은 일

- 이 결과는 kernel과 시도 단위의 비용이다. 방법(RODAS5P tableau, controller, 허용오차)과 결과 bit는 그대로다.
- facade의 banded 경로 kernel은 소유자 결정 OD-L1-9에 따라 node V22(`../banded_kernel_route/`)에서 띠 폭에 따라 고른다. 근거: Slices는 넓은 띠에서 이득이고(1.3절), 띠 2에서는 명령어가 Indexed의 0.980배인데 cycle은 1.143배다(authoritative). 보호 파일의 kernel 자체는 바꾸지 않았다.
- cycle 판정이 NOT_DECIDABLE인 칸은 조용한 호스트에서 같은 명령으로 다시 재면 된다(재측정은 cell당 2회까지, 기록은 모두 보존).
- 탐색 기록(판정 아님): 같은 코드를 `-C target-cpu=x86-64-v3`로 build하면 넓은 band 문제에서 Slices kernel의 명령어가 더 줄고 상태 hash는 같다. 수치는 `logs/xflag_v3_instructions.log`에 있다(결과 파일에는 없다).
- 다음 병목: tight kernel 뒤에는 stage 산술(보호 driver의 선형결합 loop)과 RHS가 남는다. 이 부분은 보호 driver 안에 있어 client로는 바꿀 수 없다.
- 후속 후보(판정 아님, 리뷰 자료): 대입 순서를 바꾸고 나눗셈을 유지한 tight kernel(TD)은 bit 동일은 아니지만 backward error 기준을 지키고 cycle이 더 적다(1.2절 표의 TD 행). bit 동일을 요구하지 않는 선택형 client로 다룰 수 있다.
