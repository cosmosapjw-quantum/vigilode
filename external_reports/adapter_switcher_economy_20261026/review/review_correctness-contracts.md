## Findings

### F1 (BLOCKER) Entry-pilot work ceiling can fire inside the router's band verification and abort the whole adapter solve with lost accounting
- `crates/vigilode/src/switching.rs:787` passes `Some(entry_ceiling)` to `run()`; `crates/vigilode/src/solve.rs:170-175` builds the `Guard` with that ceiling *before* `build()`, so every wrapped callback, including the ones the router calls before the first step, is charged against it.
- For `Jacobian::Dense` + a declared `band`, the plan is `Plan::Routed { declaration: Some(..) }` (`solve.rs:799-821`); `route_problem` returns `RoutedDriver::Banded` for any declared band (`routing.rs:250-253`) and `integrate_rodas5p_routed_observed_with_options` runs `verify_declared_band` unconditionally (`routing.rs:474-479`). Verification calls the facade's band fill (`solve.rs:803-813`, which calls `dense`, charged `n` units via `call_charged`) and `problem.dense_jacobian` (another `n` units), i.e. `2n` units.
- When the charged total exceeds the ceiling, `Guard::call_charged` returns `CoreError::FatalCallback` (`fd.rs:135-144`); `verify_declared_band` maps it to `StructureError::BandVerificationFailed` (`routing.rs:323`, `335-337`), the facade maps that to `SolveError::StructureRefused` (`solve.rs:207-210`), `run()` turns it into `Err(String)` (`switching.rs:1207-1215`), and `drive_windows` takes the `Err(message)` branch (`switching.rs:828-836`): `accounting_complete = false`, "implicit pilot failed without a work record; stop", `break 'windows`.
- Scenario: `evidence_driven(ProvidedOnly)`, a 12-dimensional problem with a dense Jacobian and `.band(1,1)`; an explicit batch completes its window in 3 attempts with 1 rejection (`rejection_fraction` 0.33 >= 0.3 -> pressure) with `work_units` ~ 20 -> `entry_ceiling = floor(0.8*20) = 16 < 2n = 24`. The band fill charges 12, the dense Jacobian takes the total to 24 > 16 -> the solve returns `Ok` with `success = false`, `accounting_complete = false`, message "band verification failed: dense Jacobian: Jacobian callback ... exceeds the work ceiling 16", and the 24 charged callback units appear in no counter. At `4fe67602` the same request ran the pilot, discarded it and continued on the explicit route. This contradicts "every call made stays counted" and "neither bound changes a decision" (PREREGISTRATION change 1) and AGENTS.md section 2.5.
- Fix: in `solve_observed_bounded`, when the driver/router returns `Err` and `guard.ceiling_hit().is_some()`, return `Ok(Solution)` with `Status::Failed(WorkCeilingReached)`, zero attempts and the verification's charged work (tally per-callback units in the `Guard`), or exempt the pre-step verification by arming the ceiling only once the driver loop starts (e.g. `ceiling.max(2n + 1)` for the declared-band plan; the pass test is separate, so a larger ceiling never changes a decision). Add a declared-band pilot contract test; no switching test uses `.band(`.

### F2 (MAJOR) The recheck trend re-arm cannot advance a recheck: the coalesced implicit batch always ends exactly at the scheduled recheck
- `switching.rs:589-604`: an implicit batch covers `until_recheck = recheck_interval(probe_discards) - since_probe` windows (or `residence - implicit_windows`), capped only by `window_count`. After success `since_probe += windows` (`switching.rs:888`), so `since_probe >= recheck_interval(probe_discards)` holds at the next window and `probe` is true (`switching.rs:539-541`) whether or not the re-arm at `switching.rs:881-886` fired; the re-arm sets `since_probe = probe_interval.max(windows)`, which schedules the very same window.
- The implicit rate is only observed at the end of the coalesced run, so a stiff-to-smooth transition early in a backed-off tenure (up to `probe_interval * probe_backoff_factor^2 = 16` windows) is still detected only at that tenure's end. The only live effect of the re-arm is `probe_discards = 0` for the *following* interval. PREREGISTRATION change 4 ("re-arms it") and the `probe_backoff_factor` doc ("re-arms the recheck at once") are therefore not supported as a timing mechanism; the test `return_to_explicit_still_happens_after_a_stiff_to_smooth_transition` bounds the return by `2 * probe_interval * probe_backoff_factor = 16` windows, exactly the maximum backed-off interval, so it cannot detect the inert re-arm.
- Scenario: `stiff_forced`-like problem, second recheck discarded at window 9 -> next implicit batch spans windows 9..16 (8 windows). If the stiffness drops at window 10, the rate fall is only seen after window 16; "at once" would have been a recheck at window 11.
- Fix: coalesce at most `probe_interval` windows per native run and evaluate the re-arm between chunks (recheck now, or continue the backed-off wait), or implement the rate check inside the native run via the drivers' accept-control stop (`DriverStopReason::ClientStop`); otherwise amend the registered claim to "resets the back-off after the scheduled recheck".

### F3 (MINOR) Sub-resolution window endpoints in a coalesced implicit batch abort the solve where the legacy adapter skipped them
- `switching.rs:638-645` builds `landings` from consecutive `window_target`s filtered only by `t > start`; `solve_observed_bounded` (`solve.rs:156-168`) filters by the span but never dedupes, and `OutputSchedule::new` rejects any non-increasing pair (`output.rs:475-479`). `run()` then returns `Err`, and `drive_windows` sets `accounting_complete = false` and stops (`switching.rs:662-666`). The explicit session dedupes its schedule (`switching.rs:414-420`) and the single-window path skipped such windows (`switching.rs:536-538`), so this is a regression only on the coalesced implicit path.
- Scenario: `t_span = (2^50, 2^50 + 1.0)` (ulp 0.25), `window_count = 16`, `ProvidedOnly` with `implicit_pilot_attempt_budget = 0` on a stiff problem: windows 3 and 4 both round to `t0 + 0.25`; the first coalesced batch that includes both as landings fails with "output schedule must be strictly increasing" and the solve ends with `success = false`.
- Fix: dedupe `landings` against the running last value (`t > last`, as the explicit session does) and let `solve_observed_bounded` drop duplicates; add the tiny-window contract for the implicit route (`zero_span_and_representationally_tiny_windows_do_not_loop` only covers `Forbidden`).

### N1 (NOTE) The `carry_explicit_step == false` recheck now runs a scoped session over `(start, t1)` instead of `Dopri5::solve((start, target))`
- `switching.rs:1116-1125`: probes always use `with_session` with `times = [start, target, t1]`. `target` becomes an interior landing (`limit_step` / `land_capped`) instead of the span end (`adaptive_end_step`, `below_min_step` against `t1`), so the probe's attempt sequence is not guaranteed identical to the legacy probe in rounding-residue cases, and the probe's public driver record now describes a `(start, t1)` session. Pinned flags are preserved: `initial_step = h0.min(target - start)`, `proposed_next_step = None` when carry is false (`switching.rs:1165`), success/budget flags equivalent (a landing on `target` with `AttemptBudget` is still a success). No threshold changes; disclose in the preregistration since G2 compared counts only on the measured cells.

### N2 (NOTE) Global budget exhaustion at an interior landing of a coalesced batch is now reported as an implicit driver failure
- `switching.rs:869-876`: the coalesced run stops with `MaxStepsReached` (`t < tf`), so the segment is `success = false`, `evidence = Uncompared`, `windows` = requested count, and the message is "implicit driver stopped; preserve partial accepted state" instead of the legacy "implicit window completed" + "total attempt budget exhausted" (`switching.rs:403-407`, `569-571`). Final time and state are identical; only the public message and segment flags differ.

## Checked and found consistent
- Pilot ceiling vs pass test: `charged > floor(r*W)` with integer `charged` implies `charged > r*W`; every charged callback is also counted in `WorkCounters` before user code (`problem.rs:594`, `681`, `783-826`, `operator.rs:413`, `dopri5.rs:355`; band verification merged at `routing.rs:506`), so `work_units >= charged` and a ceiling stop never changes a decision (outside F1).
- Explicit probe ceiling: same `rhs_calls` counter as `work_units`; checked only on `Yield`, so a stop always precedes the landing attempt and cannot flip an `economical` verdict by rounding.
- Discarded trials: pilot borrows `result.final_state`, probes commit only when economical; `local.h0`/`local.max_steps` are reassigned before every use; attempts/RHS charged exactly once per record (`charge` at `switching.rs:677`, `790`).
- `commit`: landings are strictly between `start` and `reached_time` in schedule order; `final_state`/`final_time` always end at `reached_time`; the `else if` branch is dead but harmless.
- Pilot back-off/re-arm: cooldown sequence 4, 8, 16 matches the recorded decision sequences; `rate = INFINITY` (no progress) cannot re-arm; a pilot requires `reached_time > start`.
- Direct paths: `Rodas5p::solve` delegates with `&[]`/`None`, same schedule, `Guard::default()`, no ceiling branch taken; session `stats_since` reproduces the former delta arithmetic.
